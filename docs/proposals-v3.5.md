## P1 — attach MUST reject a "full" grant on a subscribe-only topic (§14)

A `full` grant on a `replication: "subscribe-only"` topic negotiates mutual full-sync against a topic with no durable log: HAVE advertises the persistent stream heads (§14 ring head rule), the peer WANTs ranges that no responder can serve, and the deficit loop spins until anti-entropy noise settles. The topic table shape ADHDev uses (mixed full-sync and subscribe-only topics in one grants map) makes this an easy host mistake. Amendment: add to §14 `attach` — "a grant of `full` for a topic whose policy is `subscribe-only` throws (grant `serve` instead)". Implemented.

## P2 — `stats()` observability surface (§14, additive)

The host-guide's baseline metrics (per-topic fgen age, log/pending/quarantine/archive sizes, consumer cursor lag, per-peer queue depth and dirty-stream counts) need a supported API rather than SQL spelunking. Implemented as `SeqscribeNodeExt.stats(): NodeStats` — exact shape in `src/node.ts`. Amendment: add to §14 as OPTIONAL (implementations MAY omit; shape normative when present).

## P3 — cross-process ownership enforcement note (§8)

§8's "single-process ownership MUST" names the requirement but no mechanism, and SQLite's own WAL locking does not deliver it (two seqscribe processes corrupt each other's caches silently). The better-sqlite3 adapter now enforces it by holding `BEGIN EXCLUSIVE` on a sibling `<db>.lock` database — an OS-level file lock that dies with the process, so a crashed owner never wedges the DB. Amendment: one sentence in §8 — "storage adapters MUST enforce single ownership with a mechanism that survives owner crash (e.g. an OS file lock); an in-process flag alone does not satisfy this section."

## P4 — `webSocketChannel`'s readyState test excludes every non-WebSocket transport (§14 `Channel`, DESIGN §8)

`webSocketChannel` gates sends on `ws.readyState === OPEN` where `OPEN = 1` (`src/ws.ts`). That numeric constant is a WebSocket API detail, and the two other transports a host is most likely to bring do not match it:

- **`RTCDataChannel`** — `readyState` is the **string** `"open"`. `"open" === 1` is false.
- **wrapper channel objects** (e.g. node-datachannel wrappers, as used by ADHDev's daemon) — often expose no `readyState` at all, only a predicate such as `isOpen()`. `undefined === 1` is false.

In both cases the check is *permanently* false, so `send()` never takes the direct branch and every frame — including HELLO — accumulates in the `preOpen` buffer. The `"open"` event listener that would flush it is also WebSocket-specific, so on an `RTCDataChannel` the buffer is never drained and the session never leaves the handshake. The failure is silent: no throw, no close, just a session that never reaches `ready`.

Evidence: ADHDev could not reuse `webSocketChannel` for its WebRTC path and wrote `seqscribeDataChannel` (`packages/daemon-cloud/src/daemon-p2p/seqscribe-channel.ts`) — an adapter that differs from `webSocketChannel` almost exclusively in the readiness predicate and the pre-open flush trigger. Its unit suite pins the behavior: an open channel must send on the first `send()`, and pre-open frames must flush **in order** ahead of the frame that triggered the flush.

Two candidate amendments (not mutually exclusive):

1. **Generalize the predicate.** Treat a channel as open when `readyState === 1 || readyState === "open" || (typeof isOpen === "function" && isOpen())`. Keeps one adapter for all three shapes; costs a slightly looser `WebSocketLike`.
2. **Ship `dataChannelChannel()`** as a sibling export for the `RTCDataChannel`/predicate shape, and add one sentence to DESIGN §8 stating that `webSocketChannel` is WebSocket-specific and other transports need their own adapter.

Either way, the pre-open buffer deserves a **bound**. Today it is an unbounded array, so a transport that never opens grows it without limit — a slow leak in exactly the failure mode above. ADHDev's adapter caps it (dropping with a reason callback), which is safe because sync already recovers dropped frames via anti-entropy.

**Status: implemented 2026-08-26** — predicate generalized per (1) with `dataChannelChannel` aliased per (2); pre-open buffer capped at 1,024 frames; flush also fires on the first post-open send so a transport whose `open` event predates wiring still drains, in order. Regression suite: `test/channel-adapter.test.ts` (ws/rtc/predicate shapes × immediate-send, ordered flush, silent-open, bounding). ADHDev's `seqscribeDataChannel` can now be retired in favor of the library adapter.

## P5 — `Store.init` acquires the owner lock, which makes a host's own `acquireOwnerLock()` a footgun (§8)

`SqliteHandle` exposes `acquireOwnerLock()`/`releaseOwnerLock()` as part of the public adapter surface, and host-guide §1 tells hosts to "provide the adapter and honor the ownership lock" — which reads as an instruction to take the lock. But `Store.init` (`src/store.ts`) *already* calls `acquireOwnerLock()` inside `createSeqscribe`, and `betterSqlite3Handle` tracks ownership with an in-process `owned` flag that throws `DB already owned by this process` on a second acquire.

So a host that follows the guide's apparent advice and acquires the lock before constructing the node turns **every successful open** into `ERR_DB_OWNED` — an error whose message ("owned by another process") states the opposite of what happened. It is easily misread as a real conflict, and the natural "fix" (retry, or delete the lock file) is worse than the bug.

Encountered exactly this while wiring ADHDev's `openSeqscribeNode`: the acquire looked like host diligence and produced a self-inflicted ownership error on a DB no other process had touched. The resolution is to let the library own the lock entirely and catch `ERR_DB_OWNED` from `createSeqscribe`.

Proposed, in decreasing order of preference:

1. **Make `acquireOwnerLock()` idempotent per handle** — a second acquire from the same handle is a no-op rather than a throw. The distinction the flag is trying to make (this process vs. another) is already carried by the underlying file lock.
2. **Document ownership as library-managed** in host-guide §1: hosts supply the adapter and MUST NOT call `acquire`/`releaseOwnerLock` themselves; the lock is taken by `Store.init` and released by `node.close()`.
3. **Distinguish the messages** — `ERR_DB_OWNED` for a real cross-process conflict, a distinct `ERR_MISUSE` for a double acquire from one handle, so the error text stops pointing at the wrong cause.

**Status: implemented 2026-08-26** — (1) applied to all three adapters (better-sqlite3, sqlite-wasm, Durable Object); (2) host-guide §1 rewritten (library-managed, host calls are needless no-ops, `ERR_DB_OWNED` = real conflict only); (3) subsumed by (1) — the only remaining throw is the genuine cross-process case ("lock file held"). Regression: `test/channel-adapter.test.ts` P5 block, including host-acquires-first and second-process-refused.

> The four below were surfaced 2026-08-26 by the wire-boundary hardening pass (structural validation extended to all 19 message types — `src/messages.ts`, regression in `test/wire-hardening.test.ts`). Each is a place where the SPEC states the sender's obligation but not the receiver's remedy, or leaves a bound unstated that a hostile peer can exploit.

## P6 — §5.2 names the credit obligation but no receiver remedy, and no flow-control ErrCode exists (§5.2, §16 error codes)

A conforming sender keeps unACKed data frames ≤ INFLIGHT_CREDITS and ACK advances only to contiguous, so any legitimate frame satisfies `mid ≤ recvContigMid + INFLIGHT_CREDITS`. A frame beyond that window is not congestion — it is a protocol violation — yet §5.2 specifies nothing for the receiver, and unbounded tolerance means unbounded `recvBuffer` growth. Implemented: over-credit frame → ERR + session close (mids and credits reset on redial, so a buggy-but-honest peer recovers). The ERR rides `ERR_ENTRY_ENCODING` because no flow-control/protocol-violation code exists. Amendment: state the remedy in §5.2 and add a distinct code (e.g. `ERR_PROTOCOL`) to the error table.

## P7 — chunked reassembly has no total bound: `of` is unbounded (§5.4 SNAP/SNAPSHOT/HAVE, §16)

Every frame is individually capped by MAX_FRAME_BYTES, but SNAP/SNAPSHOT `of` and HAVE `of` (pagination) are unbounded, so a hostile peer can stream arbitrarily many distinct in-range chunks into one reassembly map — memory bounded only by the peer's patience. PROBE `seqs` length is likewise frame-capped only (our emitter stops at 32). Implemented: chunk indices are validated into [1, of], but `of` itself is taken on faith. Amendment: a §16 constant (e.g. `MAX_REASSEMBLY_BYTES`, with reassembly abandoned + ERR beyond it) and an explicit PROBE seqs cap.

**Status: implemented 2026-08-26** — `MAX_REASSEMBLY_BYTES` (default 67_108_864 = 256 × MAX_FRAME_BYTES; ≥ the largest library-bounded legitimate body, a ring-tail SNAP of RING_DEFAULT × MAX_ROW_BYTES ≈ 43.7 MiB after base64; tunable via `resolveConstants`) enforced delta-aware on all three reassemblies — SNAP chunk maps (`src/subs.ts`), SNAPSHOT assemblies (`src/snapshot.ts`, which also un-marks the content-derived snapshotId as requested so an honest peer can re-serve it after redial), and HAVE page accumulation (`src/sync.ts`). Overflow = protocol violation: ERR + session close at every site, the same discipline as the §5.2 credit-window bound, with the abandoned map freed. PROBE `seqs` is capped at 64 at parse (`src/messages.ts` MAX_PROBE_SEQS — 2× the emitter's 32-point sweep). Regression: `test/wire-hardening.test.ts` "chunked reassembly total bound" block (under-cap completion, over-cap SNAP/HAVE/SNAPSHOT close-and-free, PROBE parse bound).

## P8 — the §1 charters admit `__proto__` (§1, §5.4)

`TOPIC_RE` and `WRITER_RE` both match `__proto__`, and wire record maps keyed by charter names (grants, HAVE vectors, cut maps) are plain objects at most merge sites — an own `__proto__` key arriving from JSON.parse becomes a prototype *set* under index-assignment or `Object.assign`. Implemented: wire-level rejection of an own `__proto__` key in every record map. Amendment: exclude `__proto__` in the §1 charters themselves so the name is invalid at every layer (author append and import included), not just on the wire.

## P9 — `SUB.params` is typed required but the wire form is optional (§5.4)

`MsgSub.params: JsonValue` is required in the §5.4 table, but the emitter passes `undefined` through `JSON.stringify`, which drops the property — so the on-wire reality is optional and a strict second implementation would reject frames ours emits. Implemented: the validator accepts an absent `params`. Amendment: mark it optional in the §5.4 table (absent ≡ no params).

## P10 — surface repeated HELLO non-response as an actionable peer signal (§5.1–5.3, §14)

A session starts a retried HELLO request and a five-second deadline (`src/session.ts:94-95`; `HELLO_TIMEOUT_MS = 5_000` at `src/constants.ts:32`). Expiry calls the same reasonless `close()` used by transport closure and protocol failure (`src/session.ts:240-250`). `manageReconnect` then schedules another dial indefinitely, with exponential backoff capped at 30 seconds; it resets the backoff only after `ready`, and `onError` covers dial/attach exceptions rather than pre-ready session closure (`src/host.ts:164-178`, `src/host.ts:196-219`). Consequently a reachable but non-speaking endpoint can remain a silent reconnect loop with no supported threshold at which the host can warn or stop dialing.

Proposal: add a reasoned pre-ready-close signal and a reconnect-level option such as `onPeerUnresponsive({ peerId, consecutiveHelloTimeouts })`, fired after configurable N consecutive HELLO timeouts. The callback should let the host alert and either continue or suppress further dialing; a successful `ready` resets the count. This is additive and need not change the default reconnect policy.

**ADHDev 실증 근거.** A dashboard endpoint was misclassified as a seqscribe peer, producing attach → five-second close → redial flapping for days without an error or warning. A library-level HELLO-unresponsive signal would have identified the classification error immediately.

**Status: implemented 2026-08-27** — every session close now carries a `SessionCloseReason` (`hello_timeout` distinct from `transport`/`protocol`/`stall`/`detach`/`node_closed`; queryable via `PeerHandleExt.closeReason()` — see P16), and `manageReconnect` gains `unresponsiveAfter` (default 3) + `onPeerUnresponsive({peerId, consecutiveHelloTimeouts})`, fired at the threshold and on each further consecutive timeout; returning `"stop"` suppresses further dialing, a `ready` session resets the count, and the default reconnect policy is unchanged when the callback is absent. Regression: `test/host-ergonomics.test.ts` P10 block (threshold + stop suppression, ready-resets-count).

## P11 — make `append` failures one asynchronous contract, or document the split (§14)

The public signature promises `Promise<EntryId>` (`src/types.ts:313-317`), but several preflight failures escape synchronously before a Promise exists: closed node, unknown topic, and JSON encoding validation (`src/log.ts:158-185`), plus raw append misuse on register topics (`src/node.ts:194-203`). Failures after enqueue — including a sealed writer, HLC stamping, complete entry validation, and the MAX_ENTRY_BYTES check — reject asynchronously (`src/log.ts:694-747`). A caller therefore needs both `try/catch` around the call and rejection handling on the returned Promise.

Proposal: prefer making all public append paths return a rejected Promise (for example, move preflight into an async boundary). If synchronous validation is intentionally retained, specify the two error phases explicitly in the API documentation and show the one safe calling pattern. Apply the same rule consistently to register mutation helpers that promise `Promise<EntryId>`.

**ADHDev 실증 근거.** The integration had to wrap appends with both synchronous `try/catch` and `.catch`/`await` rejection handling. Missing either half turns an ordinary validation failure into an uncaught exception or unhandled rejection.

**Status: implemented 2026-08-27** — every data-dependent preflight failure (closed node, unknown topic, JSON encoding) now rejects the returned Promise; SPEC v3.4 already states the rule this restores ("Promise-returning APIs reject", §14 error carriage), so no amendment text is needed beyond the §11.1 note below. Register mutation helpers inherit the same path through `core.append`. The single surviving synchronous throw is §11.1's raw append on a register topic — the SPEC pins that case as "throws", and it is a static API misuse knowable at development time, not a runtime condition; the split is documented in host-guide §1.5 with the one safe calling pattern (`await`/`.catch` only). Regression: host-ergonomics P11 block; `test/hygiene.test.ts` closed-surface expectation updated to the async contract.

## P12 — provide an opt-in JSON sanitizer for explicit `undefined` (§4 encoding, §14)

`assertJsonValue` deliberately rejects explicit undefined object properties (`src/encoding.ts:30-58`), and append runs it synchronously before enqueue (`src/log.ts:169-172`). That strictness is correct for canonical hashing, but `{ k: undefined }` is a routine JavaScript payload shape and every host that accepts loosely shaped application objects must independently normalize it.

Proposal: export an opt-in `sanitizeJson(value)` helper, or an explicit append option, that recursively removes undefined object properties before validation while retaining the strict default. Array behavior must be specified without changing positions — preferably reject undefined array elements (or convert them to `null` only under an explicitly named mode). The result must still pass `assertJsonValue` and JCS unchanged thereafter.

**ADHDev 실증 근거.** ADHDev ledger payloads contained explicit undefined properties, so the integration implemented its own recursive stripping pass before append. A canonical library helper would remove duplicated, easy-to-diverge normalization code.

**Status: implemented 2026-08-27** — `sanitizeJson(value)` exported from the package root: recursively drops undefined object properties into a fresh non-mutated tree, throws `ERR_ENTRY_ENCODING` on undefined array elements (positions are load-bearing under §4 — no silent shift or null coercion; the proposal's named-mode conversion was not taken) and on everything else `assertJsonValue` rejects; an own `__proto__` key survives as data (built via `Object.fromEntries`, never index-assignment). Output passes `assertJsonValue` and JCS unchanged. The strict append default stands. Regression: host-ergonomics P12 block (recursive strip, array rejection, `__proto__`, end-to-end append).

## P13 — expose append-oriented entry-size estimation before allocation (§2, §16)

The limit is `MAX_ENTRY_BYTES = 65_536` (`src/constants.ts:5`) and enforcement measures the JCS serialization of the complete `LogEntry` (`src/codec.ts:106-115`). `assertEntrySize` is already exported (`src/index.ts:36-44`), but it accepts a fully constructed `LogEntry`; an append caller does not yet know library-owned fields such as writer, seq, HLC, and chain. The actual failure therefore arrives only after enqueue when the library constructs and validates the entry (`src/log.ts:716-737`).

Proposal: export an append-oriented helper such as `estimateEntryBytes({ topic, kind, payload, key?, causal?, ref? }, context?)`, returning an exact value when node context supplies the next-entry metadata, or a documented conservative upper bound otherwise. A companion `canAppend` result may include the configured limit and estimated bytes. `assertEntrySize` remains the authoritative final check.

**ADHDev 실증 근거.** ADHDev projections implemented their own byte cap and digest-only downgrade path so oversized materialized payloads could be reduced before append. A supported estimator would make that fallback predictable and reusable.

**Status: implemented 2026-08-27** — `estimateEntryBytes(shape, ctx?)` exported (`shape` = the caller-known half: topic/kind/payload/key?/causal?/ref?; `ctx?` = writer/seq/hlc): exact when ctx supplies the next-entry metadata (chain is fixed-width 64 hex), a monotone conservative upper bound otherwise (max-length writer, 16-digit numeric fields). Compare against `Constants.MAX_ENTRY_BYTES`; the companion `canAppend` was not added — the estimator plus `resolveConstants()` covers it without new surface. `assertEntrySize` at commit remains authoritative. Regression: host-ergonomics P13 block (exactness, bound monotonicity, over-limit pre-flagging).

## P14 — define a supported runtime topic activation/reopen protocol (§6 schema negotiation, §14)

The local registry can add a previously unknown topic at runtime: `defineTopic` delegates to `TopicRegistry.define`, which only forbids changing the policy of an existing topic (`src/node.ts:188-192`, `src/topics.ts:82-98`). The operational limitation is peer activation: grants must name already defined topics at attach (`src/node.ts:211-215`), and the host guide consequently requires topic definitions before attach (`docs/host-guide.md:28`). There is no node-level API or documented choreography for a topic discovered after boot to become negotiated across existing peers; hosts must coordinate definitions and detach/reattach (or reopen nodes) themselves.

Proposal: either add a runtime topic-definition/activation API that coordinates schema-hash negotiation and session grant refresh, or document an official reopen/reattach pattern with ordering, failure, and mixed-schema behavior. Keep policy replacement a coordinated fleet schema change; this proposal concerns adding a new topic, not mutating an existing definition.

**ADHDev 실증 근거.** ADHDev creates mesh containers after process boot. Local `defineTopic` alone could register their topics, but could not make those topics available on already established daemon sessions, forcing lifecycle choreography outside the library.

**Status: resolved 2026-08-27 (via P15 + documented choreography)** — runtime activation is now: `defineTopic` on both endpoints, then `updateGrants` on each side's handle (or `ReconnectHandle.updateGrants`, which also covers future redials). The P15 re-advertisement carries schema hashes, recomputes refusals, and triggers an immediate HAVE round — no detach/reattach, no node reopen. Ordering is free (whichever side updates last completes the mutual pair; until then the topic simply isn't mutual), mixed-schema behavior is per-topic refusal (ERR_SCHEMA_MISMATCH) with the session staying ready. Choreography documented in host-guide §1.5. Mutating an *existing* topic's policy remains a coordinated fleet schema change, exactly as before.

## P15 — re-advertise grants when topics become available on an established session (§5.4 HELLO, §14)

Attach grants are fixed session input (`src/types.ts:320-327`, `src/sync.ts:164-190`). HELLO serializes that grant map with each topic's current schema hash (`src/session.ts:254-260`), then stores the peer's grants once; after `ready`, duplicate HELLO is ignored (`src/session.ts:309-334`). `defineTopic` neither updates sessions nor emits a control message. Thus a topic defined after handshake cannot become mutually full/servable until a new session is attached, even if both endpoints now have matching definitions.

Proposal: add a versioned grant-update/re-advertisement mechanism for established sessions. A safe design must validate newly named local topics, carry schema hashes, recompute refused/mutual relations, and trigger an immediate HAVE round for newly mutual-full topics. If renegotiation is intentionally out of scope, expose and document an explicit `reattachForGrants` operation rather than leaving mutation of the original grants object as an apparent but ineffective path.

**ADHDev 실증 근거.** ADHDev Stage 2 defines container topics lazily, which conflicts with attach-time grant snapshots. The integration recorded this as a gap that must be closed before Stage 4 dynamic topic rollout.

**Status: implemented 2026-08-27** — versioned grant re-advertisement on established sessions. `PeerHandleExt.updateGrants(grants)` replaces the session's grant map (full replacement, revalidated under the §14 attach ACL guard including defined-before-grant), bumps a `grantsGen` carried in HELLO (extension fields `grantsGen`/`ackGen`, absent ≡ 0 / not-an-ack), and re-advertises via the §5.3 request machinery — retried every CONTROL_RETRY_MS until the peer answers with `ackGen === grantsGen`, so a dropped frame cannot silently strand the update. The receiver applies gen-newer maps (gen dedup makes handshake retries no-ops), recomputes refusals from the current grant pair (ERR_SCHEMA_MISMATCH per newly refused topic; the session stays ready), and each applied update triggers an immediate HAVE round on both sides, so pre-existing backlogs on the new topic converge without waiting for anti-entropy. Mutating the original attach-time grants object is now provably ineffective (the session copies it). `manageReconnect` accepts a `grants` thunk and `ReconnectHandle.updateGrants` so redials do not regress to attach-time grants. Interop: pre-P15 peers ignore the extension fields and post-ready HELLOs — the update then never acks (1 frame per CONTROL_RETRY_MS until close); both endpoints must run ≥ this build for runtime activation, which is the vendored-fleet reality. Regression: host-ergonomics P14/P15 block (live activation < ANTI_ENTROPY_MS, backlog via triggered HAVE round, mismatch refusal without close, ACL revalidation).

## P16 — make peer-session lifecycle events complete and reasoned (§14)

There is a partial hook today: `PeerHandle` exposes `state()` and `onStateChange(attached | ready | closed)` (`src/types.ts:217-222`). It is not a complete lifecycle feed. The session is already `attached` before the handle is returned, and listener registration does not replay current state (`src/session.ts:52-53`, `src/session.ts:102-109`, `src/sync.ts:211-216`), so a normal caller cannot observe the initial attached transition. `close()` emits only `closed`, without cause (`src/session.ts:240-250`), making HELLO timeout, remote channel closure, protocol rejection, stall, and explicit detach indistinguishable. `manageReconnect` consumes ready/closed internally but exposes no per-attempt lifecycle callback (`src/host.ts:196-219`).

Proposal: formalize a reasoned lifecycle event surface, for example `{ peerId, event: "attached" | "ready" | "closed" | "hello_timeout", attempt, reason? }`, with defined delivery/replay semantics. At minimum, return-time subscribers must be able to record attach, and closed events must identify HELLO timeout versus transport/protocol/host detach. The reconnect helper should forward the same events rather than requiring another wrapper.

**ADHDev 실증 근거.** ADHDev added attach/ready/close logging in its glue and used those logs to find two live integration defects. The diagnostic value was demonstrated in production, but every host currently has to recreate an incomplete version of the same instrumentation.

**Status: implemented 2026-08-27** — `attach` now returns `PeerHandleExt` (a strict superset of the §14 `PeerHandle`): `onLifecycle(cb)` delivers `{peerId, event: "attached"|"ready"|"closed", reason?}` with **replay-on-subscribe** (the full event history is delivered synchronously at registration, so a return-time subscriber records the initial attached transition), and `closed` always carries a `SessionCloseReason` (`hello_timeout` / `transport` / `protocol` / `stall` / `detach` / `node_closed`), also queryable via `closeReason()`. The proposal's separate `"hello_timeout"` event value became `closed` + `reason` — one terminal event with the cause attached. `manageReconnect` forwards the same feed via `onEvent` with the attempt number, so no wrapper is needed. `onStateChange` is unchanged for compatibility. Regression: host-ergonomics P16 block (replay for return-time and post-close subscribers, reason discrimination across close paths).

## P17 — expose durable-consumer cursor reset and explicit replay (§9, §14)

`onEntry(topic, consumer, cb)` persists a cursor under `(consumer, topic)`, creates it at rowid 0 only when that name has no row, and otherwise resumes the existing row (`src/consume.ts:61-83`; `src/store.ts:564-576`). Successful callbacks advance it durably (`src/consume.ts:121-162`). This is correct for process restart, but there is no public way to say that the derived state was discarded and the same logical consumer must rebuild. Re-registering the same name at a cursor already at head delivers nothing; `stats()` then reports `lagRows = maxRowid - lastRowid = 0` (`src/node.ts:284-305`), even though the host's replacement index is empty.

Proposal: add an inactive-consumer operation such as `resetConsumer(topic, consumer, { from: "earliest-retained" | "head" | Order })`, plus a convenience `replayFromStart`. Reset and registration must be race-safe, must reject while that `(topic, consumer)` is active, and should return the actual replay boundary. "Start" cannot silently promise genesis after cold archiving: certified rows can move from `sq_log` to `sq_archive` (`src/archive.ts:56-78`), while the current consumer drain reads only the hot log (`src/consume.ts:124-126`). The result therefore needs explicit coverage/truncation metadata, or the implementation must replay archived rows too. The common rebuild path should be able to reuse the stable consumer name without creating durable-name garbage.

**ADHDev 실증 근거.** Stage 4A materializes a per-mesh read index. Its first rebuild reused the stable consumer name, resumed the old head cursor, produced an empty index, and was in danger of passing the host's `lagRows === 0` readiness gate with confidently wrong negative answers. ADHDev had to append a rebuild generation to the consumer name (`stage4a-mesh-read-model#N`) solely to force a replay.

**Status: implemented 2026-08-27** — `SeqscribeNodeExt.resetConsumer(topic, consumer, { from?: "earliest-retained" | "head" })`. Inactive-only (a reset while that `(topic, consumer)` is registered throws `ERR_MISUSE` — the race with registration is thereby excluded); the next `onEntry` under the same stable name resumes at the installed boundary, so rebuilds reuse the name with zero durable-name garbage. Returns the actual boundary plus coverage metadata: `{ existed, from, replayFromRowid, archivedRows }` — a non-zero `archivedRows` states explicitly that "earliest-retained" is the §7.6 archive floor, not genesis (archived rows are not replayed; completeness below the cut is the snapshot basis's job). The proposal's `Order`-valued `from` was not taken — bounded positional inspection is P21's scan; `replayFromStart` is the default `from`. Caveat: reset materializes the cursor row and therefore gates archiving from that moment — re-register promptly. Regression: `test/consumer-lifecycle.test.ts` P17 block (same-name replay, head skip, active guard, archived-coverage reporting).

## P18 — expose durable-consumer deletion and garbage collection (§7.6, §9, §14)

Unsubscribing removes only the live callback; the durable cursor row remains by design (`src/consume.ts:84-88`). The store has the required primitive, `cursorDelete(consumer, topic)`, but it is internal (`src/store.ts:432-443`). The only automatic deletion path is finality-driven archival: a cursor older than `FINALITY_WINDOW_MS` is deleted and emits `consumer_abandoned` (`src/archive.ts:56-71`). Consequently renamed, migrated, or generation-suffixed consumers can gate archiving until abandonment, produce avoidable anomalies, and persist indefinitely on topics that do not reach that archival path.

Proposal: add `deleteConsumer(topic, consumer)` (or a `ConsumerHandle.dispose({ deleteCursor: true })`) with the same inactive-consumer guard as P17. A small inspection/GC surface — for example `listConsumers(topic)` and `pruneConsumers(topic, { prefix?, inactiveBefore? })` — would let hosts clean up versioned consumers deliberately. Deletion must be explicit and non-default because forgetting a durable cursor changes at-least-once restart semantics; the result should report whether a cursor existed and trigger the same archive re-evaluation as cursor advancement.

**ADHDev 실증 근거.** The P17 workaround creates a new durable name on every read-model rebuild. Old generation cursors remain after unsubscribe, so recovery itself accumulates rows that can hold the archive floor and later surface as `consumer_abandoned`. ADHDev can name the obsolete generations precisely but has no supported API with which to remove them.

**Status: implemented 2026-08-27** — `deleteConsumer(topic, consumer)` (inactive-only guard shared with P17; returns `{ existed }`; an actual deletion triggers the same §7.6 archive re-evaluation as cursor advancement, so a lagging cursor's gate releases immediately), `listConsumers(topic)` (durable rows + per-name `active` flag), and `pruneConsumers(topic, { prefix?, inactiveBefore? })` (inactive-only, filters compose, returns the pruned names — the deliberate GC path for generation-suffixed consumers). Deletion is explicit and non-default throughout; nothing implicit forgets a cursor. Regression: consumer-lifecycle P18 block, including the lagging-cursor archive-gate release.

## P19 — provide a deterministic consumer caught-up signal (§9, §14)

The consumer hub already knows when a drain pass observes no rows (`src/consume.ts:112-126`), but that state is private and `onEntry` returns only an unsubscribe function (`src/types.ts:313-320`). Hosts can poll `stats().topics[topic].consumers[name].lagRows` (`src/node.ts:284-305`), but polling adds latency and races with a moving head; fixed event-loop yields are even less defensible. No public callback or Promise says that every entry through a particular observed head has completed its consumer callback and advanced the durable cursor.

Proposal: return a consumer handle with `caughtUp(): Promise<{ throughRowid: number }>` and/or `onCaughtUp(cb)`. The contract should snapshot the topic head when requested and resolve after the cursor reaches that head; later appends begin a new interval rather than preventing resolution forever. Callback failure/backoff must delay resolution, unsubscribe/close must reject it, and a reset from P17 must establish a new catch-up generation. Where rowid is intentionally private, expose an opaque high-water token instead.

**ADHDev 실증 근거.** Stage 4A's readiness gate needs proof that its materialized index contains everything already present locally. ADHDev had to implement its own `lagRows === 0` polling loop, and its earlier parity reader approximated drain completion with two zero-delay timer turns. A library signal would remove both timing guesses and make the cutover gate event-driven.

**Status: implemented 2026-08-27** — `consumerCaughtUp(topic, consumer): Promise<{ throughRowid }>`: snapshots the topic head at call time and resolves once the durable cursor reaches it — i.e. every entry through that head has completed its callback AND advanced the cursor; later appends begin a new interval and never defer resolution. Callback failure/backoff delays resolution by construction (the cursor does not advance); unsubscribe and node close reject the pending promise; a P17 reset cannot race a pending catch-up because reset requires the consumer inactive, which is exactly the state that rejected the waiters. The proposal's `onCaughtUp(cb)` form was not added — the promise composes ("and/or" satisfied), and rowid stays the token since `stats()` already exposes `lastRowid`. Regression: consumer-lifecycle P19 block (event-driven gate over a backlog, immediate resolution when caught up, unregistered/unsubscribe rejection).

## P20 — document and support the multi-process host boundary (§8, host guide)

Every `createSeqscribe` constructs a `Store` and immediately calls `Store.init`, which unconditionally acquires the owner lock (`src/node.ts:93-102`; `src/store.ts:106-125`). `CreateOpts` has no read-only or auxiliary-process mode (`src/types.ts:190-198`), and the better-sqlite3 adapter enforces ownership by holding `BEGIN EXCLUSIVE` on the sibling lock database (`src/adapters.ts:17-25`, `src/adapters.ts:46-60`). The host guide correctly warns that two nodes on one database are corruption rather than degraded mode (`docs/host-guide.md:24-30`), but it does not give a deployment pattern for an application whose legitimate writers live in multiple local processes.

Proposal: at minimum, add a host-guide section that makes one process the seqscribe owner and specifies an IPC delegation pattern for append, lifecycle, backpressure, idempotency, and owner-unavailable behavior. Library support could take either of two bounded forms: a lightweight auxiliary-writer client that submits durable write intents to the owner, or a true read-only open that takes no writer identity/owner lock and cannot append, attach, mutate cursors, or run side-effecting hubs. It must not be presented as permission for two full nodes to share one database.

**ADHDev 실증 근거.** ADHDev's daemon owns `seqscribe.db`, while a separate `mcp-server` process also appends to the shared mesh ledger. The second process cannot open seqscribe, so its inline mirror writes are skipped; the daemon later detects and repairs them through parity-driven backfill. This restores data but turns a normal multi-process write into delayed repair work. A documented owner/IPC pattern or supported write-intent client would remove that structural gap.

**Status: resolved 2026-08-27 (documented — the proposal's minimum)** — host-guide §1.6 now specifies the multi-process boundary: exactly one owner process per DB, and an IPC delegation pattern for every other local process covering append intents (with idempotency keys so IPC retries stay exactly-once appends), backpressure, owner-unavailable behavior (spool or fail fast — never a direct DB open), and reads (delegate, or serve P21 scans over the same IPC; a "read-only" second SQLite open of `seqscribe.db` is explicitly unsupported). The two library-level forms (auxiliary-writer client, true read-only open) are **deferred, not rejected**: both are real surface whose shape should be driven by the first production consumer (the ADHDev mcp-server) once the documented pattern proves insufficient — revisit then. Nothing here is permission for two full nodes on one database.

## P21 — expose bounded log consumption or read-only range scans (§9, §14)

A fresh `onEntry` consumer starts at cursor 0 and drains every retained hot-log row in rowid order (`src/consume.ts:61-71`, `src/consume.ts:121-126`). The public `SeqscribeNode` has no log-read or scan operation (`src/types.ts:313-356`), although the internal store already supports canonical total-order batches after an `Order` (`src/store.ts:193-209`) and per-writer sequence ranges (`src/store.ts:248-259`). Hosts performing a recent-window audit must therefore replay the entire retained window into memory and discard out-of-scope rows themselves.

Proposal: expose either bounded consumer registration or a read-only async range API, for example `scanEntries(topic, { after?, through?, sinceHlc?, writer?, fromSeq?, toSeq?, limit? })`. `through` should pin an immutable head/high-water token so both sides of a comparison can use the same closed interval. Results must state whether the requested lower bound predates locally available hot/cold retention, preserve canonical `(hlc.l, hlc.c, writer, seq)` order, and apply a mandatory page/limit bound. A scan must not create a durable cursor or gate archiving; a bounded durable consumer, if also provided, should make those effects explicit.

**ADHDev 실증 근거.** The parity comparator initially paired a fresh nonce consumer's whole retained shadow replay with only the latest 500 legacy-ledger rows. Older shadow entries therefore appeared as `extra_in_shadow`, making the structural gate fail even when replication was correct. ADHDev corrected the host comparison to use matching windows, but a library range read with a pinned upper bound would have made the symmetric comparison natural, cheaper, and race-free from the outset.

**Status: implemented 2026-08-27** — `scanEntries(topic, { after?, through?, writer?, fromSeq?, toSeq?, limit? })` plus `headOrder(topic)` for pinning. Two mutually exclusive forms: **canonical** — hot-log rows strictly after `after` in `(hlc.l, hlc.c, writer, seq)` order, inclusive `through` as the pinned closed-interval bound (get it from `headOrder` so both sides of a comparison share one interval), `nextAfter` resume token, and `truncatedBelow` whenever cold-archived rows sit under the requested lower bound (canonical scans read the hot log only — sq_archive is not canonically indexed); **writer** — a per-writer seq range that DOES span the cold archive (hot + `sq_archive`, deduped by seq), with `nextFromSeq` resume and `truncatedBelow` = rows below the first locally held seq. Mandatory page bound (default 500, hard cap 10,000; a seq window bounds writer pages even across gaps — an under-filled page just resumes). No durable cursor is created and archiving is never gated. The proposal's `sinceHlc` folded into `after` (an `Order` is the precise form of an HLC lower bound); the bounded-durable-consumer alternative was not taken. Regression: consumer-lifecycle P21 block (pinned-interval paging with post-pin appends excluded, archive-spanning writer scan, form mixing rejected, no durable side effects).

## P22 — WANT completion must detect non-progress: the finality branch re-queues with zero backoff (§5.4 WANT/ENTRIES, §7.5, §16)

The WANT completion handler's recovery branch has absorbing-state detection — no progress ⇒ `reportCanonicalUnavailable` (`src/sync.ts:720-728`). The non-recovery (finality) branch immediately below (`src/sync.ts:729-735`) has neither progress detection nor backoff: if `m.toSeq > head.contigSeq` still holds and `awaitingSnapshot` is false, it calls `queueWant` again at once. Three co-conspirators make that unconditional re-queue an infinite, zero-delay loop:

- `src/log.ts:779-793` — `pre_finality_rejected`: when a durable finality certificate is live (valid from boot) and an incoming entry has `order ≤ cert.order` with `seq > cover`, ingest rejects and annotates **without sealing or advancing anything**. `contigSeq` never moves.
- `src/sync.ts:710` — `applyExternal(...).catch(() => undefined)` discards apply outcomes wholesale, so an all-rejected round is indistinguishable from a productive one.
- `src/sync.ts:607-681` — `serveWant` re-reads the same deficit window from SQLite and re-sends it, faithfully, every round.

Result: a peer holding entries that the local finality certificate rejects (voided rows, or a pre-finality build's leftovers) drives an unbounded WANT→ENTRIES→reject→WANT cycle that burns CPU **on both ends** — each round is a datachannel TSF wakeup, a full window of row `JSON.parse` (`src/store.ts:96` parses at read time), per-reject annotation, and (P23) un-cached statement prepares. No anomaly is logged, so the loop is symptomless in seqscribe's own telemetry.

Proposal:
1. Give the finality branch the same absorbing-state discipline as the recovery branch: track per-(topic, writer, peer) `contigSeq` progress across WANT rounds; a round with no progress must not re-queue immediately — report a new anomaly (e.g. `sync_stalled`, carrying the reject-reason histogram) and suspend re-WANT toward that peer until a new HAVE/adoption event changes the picture.
2. Stop discarding apply outcomes at `src/sync.ts:710` — an all-rejected round is the definition of non-progress and must feed the detector.
3. Backstop: route every re-queue through a minimum delay (the session-retry ~5s class), so no future non-progress condition can ever become a tight loop again.
4. Observability: surface reject-reason counters (`pre_finality_rejected` et al.) in `stats()`/anomalies — the incident was invisible precisely because rejects are silent.

**ADHDev 실증 근거.** Fleet daemon at selfCpu 84–118% with event-loop drift 6–60s; `sample` profiling showed ~46–60% of mainthread time in the datachannel ThreadSafeFunction → microtask chain (frames arriving from the peer are what keep the loop alive). Auth handshakes exceeding their 15s timeout took the daemon off the dashboard repeatedly; one process died at 1.6GB RSS and its launchd replacement resumed spinning within a minute. The vulnerable region is byte-identical in pins cdf1186 and d5e10cf, so no adopted proposal (P1–P21) covers it; regression became fleet-visible when a periodic prober began exercising the content topic (first lag warnings), then crossed a threshold into sustained spin.

**Status: implemented 2026-08-27** — (1) the finality branch now runs the recovery branch's absorbing-state discipline: per-(peer, stream) contigSeq is tracked across WANT completions, and a completed round that moved nothing does NOT re-queue — the stream **stalls** (new anomaly kind `sync_stalled`, emitted once per stall transition; per-peer `stalledStreams` in `stats().peers`), and re-WANT thereafter happens only via HAVE rounds / cert acceptance / snapshot adoption, all of which are timer- or event-paced — steady-state cost drops from a zero-delay spin to one bounded window per ANTI_ENTROPY_MS, and a round that does progress clears the stall. (2) `applyExternal` outcomes are no longer discarded: non-applied outcomes (`rejected_finality`, `sealed`, `forked`, `dropped_overflow`, `error`) accumulate into per-topic counters. (3) In lieu of a blanket re-queue delay: every WANT completion re-queue is now progress-gated (recovery branch had it, finality branch gained it, caught-up completions clear state), and every other `queueWant` entry point (HAVE rounds, directives, adoption) is timer- or event-driven — no self-feeding path remains; a global minimum-delay plumb was judged unnecessary complexity on top of that. (4) `stats().topics[t].applyRejects` exposes the reject histogram; the anomaly carries the kind, the histogram lives in stats (the SPEC Anomaly shape has no detail field — extending it was not taken). Regression: `test/sync-stall.test.ts` — the poisoned-peer incident shape (bounded WANT count over multiple anti-entropy periods, session stays ready, anomaly + counters visible) and a 250-entry healthy multi-round pull with zero false stalls.

## P23 — cache prepared statements in the better-sqlite3 adapter (§16, performance)

`src/adapters.ts:29/38/41` prepare a fresh statement for every store operation. **Status: implemented 2026-08-27** — keyed statement cache (SQL string → prepared statement) in `betterSqlite3Handle`. The SQL census is finite (fixed store paths plus per-topic/view table names); a 512-entry cap with full-clear guards pathological dynamic SQL — a clear merely re-prepares. ## P24 — expose interval sync throughput in `stats()` so hosts can distinguish "hot and busy" from "hot and stuck" (§14, observability)

P22 gave `stats()` an absorbing-state signal (`stalledStreams`, `applyRejects`) for the *no-progress* case: a peer looping WANT→ENTRIES→reject with `contigSeq` unmoved now surfaces as a stall. But the complementary case is still invisible: a peer legitimately serving or applying a large backlog — cold-start catch-up, a slow consumer's replay, a burst after reconnect — is both hot (CPU-bound in `JSON.parse`/`JSON.stringify` over every entry, per `entriesRange` batches) and *progressing*, so none of P22's detectors fire. `stats()` today has only point-in-time gauges (`logRows`, `pending`, `consumers[].lagRows`, `peers[].dirtyStreams/queuedData/stalledStreams`) — nothing answers "how much sync traffic moved in the last N seconds," which is exactly the question a host needs answered before reaching for a profiler.

Concretely: `serveWant` (`src/sync.ts:629-703`) walks `entriesRange` batches and calls `sendData` per batch with no counters kept beyond the loop's own `from` cursor. `onEntries` (`src/sync.ts:717-798`) now tracks non-applied outcomes into `this.rejects` (the P22 addition, `src/sync.ts:740-745`) but drops the applied/duplicate/pending counts on the floor (`continue` at `src/sync.ts:741`) — the very outcomes that mean "this is real, useful sync work," not just rejects. `queueWant` (`src/sync.ts:467`) has no round counter either. A host mid-incident can see `dirtyStreams`/`queuedData` are nonzero and CPU is pegged, but cannot tell from `stats()` alone whether that is this topic's sync engine moving a legitimate backlog or something else entirely on the same event loop.

Proposal:
1. Add interval (not cumulative) counters to `NodeStats`, reset each time `stats()` is read (simplest semantics, consistent with `stats()` being a point-in-time snapshot everywhere else — no separate reset call, no background timer):
   - Per-topic: `servedEntries`, `servedBytes` (from `serveWant`'s batches), `appliedEntries`, `appliedBytes` (from `onEntries`'s applied/duplicate/pending outcomes, sibling to the existing `applyRejects` counting already in place).
   - Per-topic or per-peer (whichever the existing `rejects`/`syncProgress` maps key on more naturally): `wantRounds` split by requester (`queueWant` calls) vs responder (`serveWant` calls) — a round count, not a byte count, since P22 already showed round cadence is the signal that catches loops.
   - Top-N `(topic, peer)` pairs by served+applied bytes this interval — bounded (e.g. top 5), scalars/identifiers only, so the field can't grow unbounded under many peers.
2. All new fields are scalars, counts, or identifiers already public elsewhere (`topic`, `peerId`) — no entry content, consistent with every existing `stats()` field.
3. Optional: an informational anomaly (e.g. `sync_hot`) when interval throughput crosses a constant-driven threshold, so the signal reaches `onAnomaly` subscribers without polling `stats()`. This must stay observational only — no proposed throttle or backpressure change, since the traffic it flags (bulk catch-up) is normal and correct; suppressing it would only slow down legitimate recovery.

**ADHDev 실증 근거.** A fleet daemon was observed at sustained 100%+ CPU. Because P22's stall/reject signals were both quiet (the peer was making real progress, not looping), the host could not rule sync in or out from `stats()` and had to attach a CDP profiler to get a call-stack breakdown before finding the actual cause (a host-side ledger reader, unrelated to seqscribe). P22 closed the "stuck and symptomless" gap; this incident is the "busy and symptomless" gap on the other side of the same problem — a host should be able to ask "is this sync traffic?" and get an answer in seconds from a library call, not a profiling session.

## P25 — writer-form `scanEntries` cannot see the ring-retention memory tail (§9, §14)

P21's writer-form `scanEntries` builds its result set from exactly two sources: `store.archivedEntries(topic, writer, fromSeq, windowEnd)` and `store.entriesRange(topic, writer, fromSeq, windowEnd)` (`src/node.ts:362-364`), both of which read durable rows (`sq_archive` and `sq_log` respectively). For a `retention.mode === "ring"` topic, `persist()` never writes either of those durable stores — it pushes the entry onto an in-memory `rings` Map and returns `null`, "no durable log row" by design (`src/log.ts:877-891`, comment at line 891). The only reader of that Map is `ringTail(topic)` (`src/log.ts:351-353`), which `scanEntries` never calls. The writer-form head lookup at `src/node.ts:354` (`core.getStream(topic, o.writer)`) does advance `contigSeq` past ring-tail appends — so the scan's own `head.contigSeq` default for `toSeq` and its `truncatedBelow` computation (`src/node.ts:369`) both see the entry as locally present, while the entry list itself comes back empty for that seq. A ring topic's most recent entries — the only entries a bounded ring retains — are therefore exactly the ones a writer-form scan cannot return.

Proposal:
1. Extend writer-form `scanEntries` to merge `store.core.ringTail(topic)` (filtered to `writer` and the requested `[fromSeq, toSeq]` window) into the `bySeq` map alongside `archivedEntries` and `entriesRange`, before the existing sort/complete/truncatedBelow computation — same seq-keyed dedup the archive/hot-log merge already uses (`src/node.ts:361-365`), so no new merge semantics are introduced.
2. If (1) is deferred, at minimum add an explicit signal (e.g. a `ringTailExcluded: boolean` field on `ScanResult`) whenever the scanned topic's retention policy is `ring`, so an empty `entries` array with `complete: true` cannot be misread as "no data" when a ring tail is in fact being withheld.
3. Regression: append to a fresh ring-retention topic (`size` small, e.g. 3) as writer `w`, then `scanEntries(topic, { writer: w, fromSeq: <appended seq>, toSeq: <appended seq> })` — today returns `{ entries: [], complete: true, truncatedBelow: true }`; after the fix, `entries` must contain the appended row.

**ADHDev 실증 근거.** Confirmed on pin `982c80c`: a new ring-retention topic (`size: 3`), one writer append at `seq=1`, then `scanEntries(topic, { writer, fromSeq: 1, toSeq: 1, limit: 1 })` returns `writerVectorContig=1` and `ringTailSeqs=[1]` (i.e. `core.vectors()` and `store.core.ringTail()` both see the entry) but `scanEntrySeqs=[]` — an empty page, marked `complete: true` and `truncatedBelow: true`, which reads as "this data was here once but is now gone" rather than "this data exists in memory right now and was never durable." ADHDev's Phase 4 Stage 3 parity reader hit this while building a P21-based read path over a ring topic used for its subscription-topic extraction: the vector said data was there, the scan said there was none, and the host had to fall back to a node-local snapshot read outside the library's public scan surface to get the ring tail at all.

**Status: implemented 2026-08-28** — option (1), the direct fix; the (2) `ringTailExcluded` fallback was not needed and is withdrawn. Writer-form `scanEntries` now merges the ring tail as a third source into the same seq-keyed `bySeq` map, filtered to `writer` and the `[fromSeq, windowEnd]` window, after `archivedEntries` and `entriesRange` (`src/node.ts:361-372`). Dedup, sort, `complete` and the `limit`/`nextFromSeq` window semantics are entirely unchanged — the merge introduces no new rules, exactly as proposed. Canonical-form scans are untouched: they remain hot-log-only by contract, and a ring topic has no hot log by construction.

Two corrections to the text above, from reading the source rather than the proposal draft:

- The call is `core.ringTail(topic)`, not `store.core.ringTail(topic)` — `node.ts` binds `core` (the `LogCore`) and `store` as siblings (`src/node.ts:160-168`); `store.core` does not exist. The ADHDev probe reached the same method by a different route.
- `truncatedBelow` needed **no** change, and re-deriving it against the merged result set is item (2) of this proposal discharged. The existing formula — `firstAvail > fromSeq` when the page is non-empty, else `head.contigSeq >= fromSeq` (`src/node.ts:375-377`) — is already correct for ring topics once the tail participates, because a ring evicts strictly from the bottom: the first seq the tail holds *is* the local retention floor, which is precisely what the non-empty branch measures. The empty-page branch keeps its meaning too — for a window entirely below the ring's floor, `contigSeq` has passed `fromSeq` and `true` is the right answer ("these existed and are gone"). The pre-P25 bug was never in the `truncatedBelow` computation itself; it was that an empty `entries` array forced the fallback branch for windows the ring was in fact holding, so the flag reported eviction for live data.

Regression: consumer-lifecycle.test.ts P25 block — (i) the ADHDev probe verbatim (append one entry to a `size: 3` ring, scan `fromSeq/toSeq = 1`), red before the change and green after; (ii) `truncatedBelow` accuracy across a ring that has evicted (5 appends into size 3: full tail `[3,4,5]` truncated, a window inside the tail not truncated, a window fully below it empty-and-truncated, and `limit` paging still bounded by seq window); (iii) a full-retention topic's writer scan unchanged in the same node, guarding against ring tails leaking across topics.

## P26 — `beaconFetchHandler`'s board is unhosted in-memory state; DO hibernation erases it (§14 beacon wire)

`beaconFetchHandler` (`src/beacon.ts:164-196`) closes over `const board = new Map<string, Map<string, BeaconReport>>()` and both the GET and POST handlers read/write that closure directly (`src/beacon.ts:179`, `:186-188`). The doc comment above it already flags the sharding hazard for a stateless multi-isolate Worker and says to "run it inside a Durable Object … so the board is actually shared" — but a Durable Object is not a persistent process. Cloudflare hibernates an idle DO and evicts its isolate; on the next request the DO's JS context is reconstructed from scratch, and a plain closure variable like `board` does not survive that — it resets to an empty `Map`. Every vector every node has ever PUT is gone, silently, the next time the account's DO wakes from idle. For a board whose entire purpose (§5.7, §14) is to be an always-on staleness/lag oracle nodes can GET without having been continuously connected, an eviction-triggered reset defeats the reason it exists: a peer that was legitimately ahead before the DO slept looks identical, after a hibernation cycle, to a peer that was never seen.

This is a gap in the *reference* fetch handler specifically — `httpBeaconTransport` (the client) and the wire contract (§14: `POST .../vectors`, `GET .../vectors → BeaconReport[]`) are unaffected; only the server-side reference implementation's storage is in question.

Proposal:
1. Give `beaconFetchHandler` an optional persistence-injection interface, e.g.:
   ```ts
   export interface BeaconBoardStore {
     load(account: string): Promise<Record<string, BeaconReport> | null>; // node → report
     save(account: string, board: Record<string, BeaconReport>): Promise<void>;
   }
   ```
   Keyed per-account (matching the existing `board.get(account)` granularity) rather than a single whole-board blob or per-node rows: an account's report set is small (one `BeaconReport` per active node, and `known` in `BeaconHub` is already the same shape client-side), so a per-account load/save is simple, matches DO storage's natural unit (one DO instance per account is the deployment shape the existing comment already assumes), and avoids the coordination cost of partial per-node writes racing each other inside one `save`. Reject finer-grained (per-node) persistence: POSTs already overwrite whole-node entries in the in-memory map (`src/beacon.ts:187`, "one report per node, overwrite"), so per-account read-modify-write mirrors the existing semantics exactly and needs no new merge logic.
2. Default remains the current bare in-memory `Map` — passing no `o.store` must reproduce today's behavior byte-for-byte (existing callers, including any host that already deployed `beaconFetchHandler` without a store, see zero change). `o?.store` joins the existing `o?.token` option.
3. DO usage pattern (normative guidance, not code): on cold start / first request after wake, `await store.load(account)` and seed the in-memory `Map` from it before serving; on every POST that mutates the account's board, `await store.save(...)` before returning 204 (write-through) — or debounce the save if a host wants to coalesce bursts, since board data is advisory (see next point) and losing the last few seconds of it on an untimely eviction is acceptable in a way losing the whole board is not. GET never needs to persist.
4. Concurrency/failure contract: a `save` failure MUST NOT fail the POST that triggered it — the response is still 204, and the in-memory `Map` (this isolate's copy) is already updated regardless of persistence outcome. Vectors are advisory, self-healing data (§5.7: nodes rebuild `staleness()` from whatever `known` they currently have, and every node re-PUTs its own current vector on its own debounce cycle per `notifyApplied`), so a lost or stale-read board degrades staleness *estimates* for one cycle — it does not corrupt sync, block writes, or lose durable log data. The proposal should say this plainly so an implementer does not over-engineer transactional guarantees the data's own design doesn't need.
5. Regression: (i) inject a fake `BeaconBoardStore`, POST a report, construct a *fresh* `beaconFetchHandler` instance against the same store (simulating a post-hibernation cold start), GET must return the pre-reset report — board state survives the handler-instance boundary via the store. (ii) omit `o.store` entirely — existing behavior (POST then GET on the same instance returns the report; a fresh instance with no store returns empty) must be byte-identical to pre-P26. (iii) `save` rejecting (simulated write failure) must not change the POST's response status or the in-memory board's contents for the rest of that isolate's lifetime.

**ADHDev 실증 근거.** ADHDev's Beacon-on-DO integration plan (decision D6, "Beacon only for this phase") identified this as a severity-high blocker before any code was written: a Durable Object is the natural host `beaconFetchHandler`'s own doc comment recommends, but DO hibernation is exactly the failure mode the current in-memory closure cannot survive. Flagging it here rather than working around it in ADHDev-side code because the gap is in the reference handler itself, not in how ADHDev calls it — any other DO-hosted deployment of `beaconFetchHandler` hits the same reset on the same hibernation cycle.

**Status: implemented 2026-08-28** — all five items as proposed. `BeaconBoardStore` (`load`/`save`) joins `token` as `o?.store` on `beaconFetchHandler`; **the contract is per-account**, exactly as item 1 argued, and the rejection of per-node rows stands on inspection: a POST already overwrites a whole node entry, so per-account read-modify-write mirrors the in-memory semantics with no merge logic. A host whose storage has a per-value ceiling (ADHDev's 128 KiB DO limit) shards inside its own adapter — that is a storage detail the contract deliberately does not encode. No-store path is unchanged (item 2), write-through on POST with hydrate-on-first-touch per account (item 3), and a `save` failure leaves both the 204 and this isolate's board intact (item 4).

Two concurrency behaviors the proposal did not specify, both forced by the DO setting it targets and both regression-covered beyond item 5's three cases:

- **Hydration is once-per-account-per-isolate and single-flight.** Concurrent first requests share one in-flight `load` rather than each issuing their own and clobbering the seed. A *failed* load is deliberately not marked hydrated, so the next request retries; it degrades to an empty board and a 200 rather than failing the request, on the same advisory-data reasoning as item 4.
- **A POST landing mid-hydration wins over the seed.** The load result is merged *under* whatever this isolate already accepted — a report that arrived while the read was in flight is newer than what the store held when it was read, so seeding must not overwrite it. Without this the write-then-hibernate race silently reverts a just-accepted report.
- **Saves for one account are serialized, and each snapshots the board at its own turn.** Item 3's write-through is not safe as a bare `await save(...)`: two concurrent POSTs produce two overlapping saves that can commit out of order, leaving the store holding the *older* snapshot. A node that already received its 204 is then missing after the next hibernation — a lost acknowledged write, not the "lost the last few seconds" that item 4's advisory-data reasoning actually licenses. Regression: two concurrent POSTs with the first save made slow; the last commit must contain both nodes.

## P27 — nothing in the library ever produces `BeaconReport.hints`; the pre-write-warning feature is unreachable (§5.7, §14 beacon wire)

`BeaconHub.staleness(topic, key)` reads `report.hints?.[topic]?.[key]` for every known report and, when present, surfaces it as `keyStale` — the `[writer, seq]` of the latest change to `key` that *some* peer has seen, compared against what the local replica has (`src/beacon.ts:90-101`). This is the entire mechanism behind DESIGN §5.7 feature ②, "pre-write warning — editing a register key while your vector lacks its latest known change → 'you would overwrite'." But the only place a `BeaconReport` is constructed, `BeaconHub.push()`, builds it from exactly `{ node, at, vectors }` (`src/beacon.ts:106-113`) — `hints` is never assigned, not even as an empty object. `BeaconReport.hints` and `TopicPolicy.hintKeys` (`src/types.ts:171,253`) both exist as typed surface, and `hintKeys` is validated at `defineTopic` time (`src/topics.ts:58-59`: rejects any value other than `"plain"`/`"hash"`/`undefined`) — but validating a knob that nothing downstream reads does not make the knob do anything. No code path in `src/register.ts`, `src/log.ts`, or `src/beacon.ts` reads `hintKeys` a second time, computes a hash, or attaches a key/seq pair to an outgoing report.

Consequence: every `report.hints` a `BeaconHub` ever sees — its own or a peer's — is `undefined`, so the `if (hint && ...)` guard at `src/beacon.ts:91` never passes, `latestKnown` stays `null`, and `staleness()`'s returned `Staleness` never carries `keyStale` regardless of what any peer actually did. This is silent: `staleness()` returns a well-formed object every time (`behind` still populates correctly from `vectors`, which *is* produced), so a host wiring a pre-write check sees no error, no warning, and no signal that the feature it read about in DESIGN §5.7 cannot fire — a permanently-false guard with no distinguishing symptom, the same shape of defect as P4's `readyState` check. Unlike P26 (storage layer, only the reference DO handler is affected), this gap is in the core library itself — `httpBeaconTransport`, any custom `BeaconTransport`, and `beaconFetchHandler` are all unaffected, because the wire and storage are correctly shaped to carry `hints` end to end; there is simply never a `hints` value to carry.

The two other §5.7 features are unaffected: ① wake-up lag (`behind`) is computed entirely from `vectors`, which `push()` does populate; ③ sole-copy awareness is a host-side comparison over vectors the host already has, not a library API this bug touches.

Proposal:
1. Give `BeaconHub` a supply path for hints, additive to the existing `vectors` production in `push()`. Two forms, not mutually exclusive:
   - **Host-supplied**: an optional `hints(): Record<Topic, Record<string, [WriterId, Seq]>> | Promise<...>` callback passed at `beaconHub.start(t, { hints })` (or accepted by `beacon()` on the node handle), called each time `push()` fires and merged into the outgoing `report.hints`. This covers the general case — any topic, any key shape the host wants advertised — and matches the existing pattern of the host owning what's advisory (cf. P20's deferred-not-rejected host client).
   - **Library-derived for register topics**: `RegisterHub` already tracks a per-`(topic,key)` causal scope tail — `scopeTails: Map<string, [WriterId, number]>` (`src/register.ts:104`) — updated on every commit, in-memory only, currently private. For any topic with `hintKeys` set (i.e. the host opted in), the library can read this map directly and populate `hints[topic]` without host involvement — the exact `[writer, seq]` shape `BeaconReport.hints` already declares, sourced from data the library computes for causal stamping anyway. Append-kind topics have no equivalent internal per-key tracking (`LogEntry.key` is optional and not indexed by the log core the way `scopeTails` indexes registers), so they remain host-supplied-only unless a future proposal adds one.
2. Honor `hintKeys` for real: `"plain"` emits the key as-is; `"hash"` emits a hash of the key instead (algorithm unspecified by SPEC today — this proposal does not pick one, only notes that `"hash"` currently validates and then does nothing, which is the same class of dead knob as the top-level bug). Whichever form supplies a hint for a topic with no `hintKeys` set should be rejected or silently dropped at `push()` time — consistent with treating `hintKeys` as the per-topic opt-in gate the SPEC wire format implies, not merely a validated-but-inert field.
3. Backward compatibility: a host that supplies no `hints()` callback and defines no register topics with `hintKeys` set must see byte-identical `push()` output to today — `report.hints` stays absent, exactly as now.
4. Regression: (i) a register topic with `hintKeys: "plain"`, one `set()` on a key, then `push()` — the resulting `BeaconReport.hints[topic][key]` must equal the commit's `[writer, seq]`, and a second node's `staleness(topic, key)` fed that report via `setKnownVectors` must return `keyStale` with the correct `latestKnown` and `haveLocally` computed from its own local contig. (ii) a host-supplied `hints()` callback's return value appears verbatim in the next `push()`. (iii) a topic with no `hintKeys` and no host callback produces no `hints` key on its `BeaconReport`, matching current behavior exactly. (iv) `hintKeys: "hash"` is rejected or dropped (per whichever remedy is chosen in (2)) rather than emitting the raw key, so a "hash" declaration cannot leak plaintext keys by omission.

**ADHDev 실증 근거.** While wiring a pre-write warning UI on top of `staleness(topic, key)` for the same Beacon-on-DO effort that surfaced P26, the UI never received a `keyStale` result under any test condition — including a peer that had genuinely written a newer value to the same key and successfully reported its vector. Reading `BeaconHub.push()` located the cause: no code path in the library ever assigns `BeaconReport.hints`, so the field the reader depends on is always absent, regardless of what any peer's `hintKeys` policy or actual writes were. The gap was found by source inspection, not by a failing assertion — `staleness()` has no way to signal "this feature has no data source," since an absent `keyStale` is also the correct return when no peer happens to be ahead.

**Status: implemented 2026-08-28** — both supply paths from item 1, `hintKeys` honored for real per item 2, byte-identical no-opt-in output per item 3.

**One correction to item 1: `scopeTails` is the wrong source, and using it would have shipped a feature that is empty exactly when it matters.** The proposal reads `RegisterHub.scopeTails` (`src/register.ts:105`) as "a per-`(topic,key)` causal scope tail updated on every commit". It is not that. It is the §11.2 **own-uncommitted tail** — its own comment says so — and it has two properties fatal to this use:

1. Entries are **deleted as each own write materializes** (`src/register.ts:492-494`, "the own uncommitted tail shrinks as own writes materialize"). In the steady state a hint describes — a write that committed and folded some time ago — the map is empty.
2. It only ever holds **this node's own** writes (`[this.deps.writerId, seq]`, `src/register.ts:363`). A peer's write, which is the whole point of a pre-write warning, never appears in it.

The correct source is the **materialized winner**, `KeyState.winner` — the fold's per-key judgment over the total order, which is exactly what "the latest change to this key" means, survives materialization, and covers peer and own writes alike. Implemented as `RegisterHub.hintsFor(topic)` over `winner`, falling back to the highest member entry for member-only keys (under §11.5 mirror rules such a key has no scalar `winner`, but an add/remove is still a change a concurrent editor would overwrite). The regression pins this specifically: the hint is asserted *after* the write has folded, which a `scopeTails`-based implementation would fail.

**Ranking is by total order, never by raw `seq` — on the PRODUCER side.** A key's candidates can come from several writers (the member path especially), and `seq` is per `(topic, writer)` — so comparing seqs across writers compares unrelated counters and can name a stale entry from a high-seq writer as "latest". `hintsFor` ranks with `orderCompare` over `winnerOrder`/`MemberState.order`, matching every other comparison in the fold. Regression: a two-writer mesh where wA's stream is driven far ahead, then wA and wB each add a member to one key — wB's write is later in total order at a much lower seq, and the hint must name wB.

The **reader** — `staleness()` at `src/beacon.ts:126` — still picks the largest `seq` when several peers report a hint for the same key, and then evaluates `haveLocally` against that writer's stream. That is pre-existing v3.4 code, not something P27 introduced, and it is **not fixable within the current wire shape**: `BeaconReport.hints` carries `[WriterId, Seq]` and no `Order`, so a reader has nothing to order by. Ratified as a stated limitation in §5.7a rather than silently — `keyStale` is advisory by its own §14 contract and must not be used as a correctness gate. ## P28 — `BeaconHub.stopped` is a one-way latch: `start()` never clears it, so a stop-then-restart handle silently never pushes again (§5.7, §14 beacon wire)

`BeaconHub` (`src/beacon.ts`) has exactly one `stopped` field, set to `true` by both `stop()` (the handle's own method, `:59`) and `close()` (the node-level quiescence hook, `:71`) — and read as a guard in three places: `notifyApplied()` (`:81`, `if (!this.transport || this.stopped || ...) return`), the async tail of `push()` (`:194`, `if (!this.stopped) this.known = reports`), and implicitly via `push()` itself, which is called unconditionally from `start()` (`:56`) but self-guards at `:182` (`if (!t || this.stopped) return`). Nothing in the class ever assigns `this.stopped = false`. `start(t, o?)` (`:52-56`) sets `this.transport = t`, sets `this.hostHints`, and calls `this.push()` — it does not touch `stopped` at all.

Consequence: `hub.start(transport)` → `handle.stop()` → `hub.start(transport)` again produces a `BeaconHandle` that *looks* identical to a fresh one (no throw — the `misuse("beacon already started")` guard at `:53` only fires when `this.transport` is truthy, and both `stop()` and `close()` null it out) but whose every subsequent `push()` is a silent no-op: the initial push `start()` fires unconditionally still returns early at line 182, and every debounced push from `notifyApplied()` after an append (§5.7's 5s-after-append mechanism) returns early at line 81. No exception, no rejected promise, no anomaly — `start()`'s return value gives the host nothing to inspect, and the wire is simply never written to again. A board this host previously reported to keeps serving whatever the last pre-stop report said, aging silently, indistinguishable from a healthy node whose vector genuinely stopped changing.

This is the same defect shape as P4 (`webSocketChannel`'s permanently-false `readyState` check) and P27 (a permanently-absent `hints` field): a guard that is always on one side of its branch with no distinguishing symptom on the failing path.

**ADHDev 실증 근거.** ADHDev's daemon hosts one `BeaconHub` per mesh node and re-arms it on every P2P reconnect (`stop()` on detach, `start()` on the next successful attach) — the natural pattern for a host that treats beacon as reconnect-scoped auxiliary state, mirroring how it already re-attaches seqscribe sessions themselves. Driving the library directly confirmed: first arm produces one `put()` on the transport (verified via a stub transport counting calls); `stop()` then a second `start()` on the same `BeaconHub` instance produces zero further `put()` calls across an append that would otherwise trigger `notifyApplied()`'s debounce. `beaconFetchHandler`/`httpBeaconTransport` (P26/P27's subjects) are unaffected — the defect is entirely inside `BeaconHub`'s own state, upstream of any transport call. ADHDev's workaround is host-side: arm each node's `BeaconHub` at most once for its process lifetime (never call `start()` a second time on the same instance) and use `pushNow()`-shaped re-seeding on reconnect instead of `stop()`/`start()` — sidestepping the latch rather than exercising it. A pinned regression on the ADHDev side (arm → stop → re-arm → append → expect a push) is red against the current library and is the signal to pick this proposal back up once P28 lands.

Proposal, in decreasing order of preference (the choice depends on which the library intends `stop()` to mean — full teardown eligible for reuse, or terminal for the instance — and that intent isn't recorded anywhere today):

1. **Make `start()` clear the latch**, i.e. `start()` sets `this.stopped = false` alongside `this.transport = t`. This treats `stop()` as "pause/detach, reusable," matching the handle-returning shape of `start()` itself (a handle you can `stop()` reads as something you'd expect to be able to `start()` again) and matching ADHDev's actual usage pattern (reconnect-scoped re-arm) without requiring a host-side workaround. Lowest-risk: no new error surface, no new types; `close()`'s stronger guarantee (node-level, irreversible teardown) would need its own field or a second boolean (e.g. `closed` distinct from `stopped`) so that `close()` still permanently forecloses restart even under this fix — a `BeaconHub` surviving its owning node's `close()` and being `start()`-able again would be a correctness regression in the other direction.
2. **If reuse is intentionally unsupported**, make `start()` reject it explicitly rather than silently no-op: throw `misuse("beacon already stopped — construct a new BeaconHub")` (or equivalent) when `this.stopped` is true at entry, using the same `misuse()` helper the existing `this.transport` guard already uses at `:53`. This keeps the one-instance-one-lifetime contract but removes the silent-failure mode — a host doing what ADHDev did fails loudly at the first re-`start()` instead of discovering it via a board that stopped updating.
3. Either way, extend the guard at `:53` to also cover the stopped-but-transport-nulled case (currently `if (this.transport) throw ...` misses it entirely, since `stop()`/`close()` null `transport` before `stopped` would ever be read) — today that check cannot fire in the exact scenario this proposal describes, which is why the bug reaches production silently instead of surfacing as the existing "already started" error.

Regression, either remedy: (i) `start()` → `handle.stop()` → `start()` again on the same `BeaconHub` instance, then trigger `notifyApplied()` (via an append) or call `push()`'s equivalent path directly — under remedy 1, assert the transport's `put()` is called; under remedy 2, assert `start()` throws. (ii) `close()` → `start()` again must NOT succeed under either remedy (node-level teardown stays terminal) — this is the case that distinguishes remedy 1 from a naive "just clear stopped in start()" patch, and must be pinned explicitly so a fix for the reusable-stop case cannot regress the closed-is-terminal case. (iii) the existing `misuse("beacon already started")` path (`start()` called twice without an intervening `stop()`/`close()`) must be unchanged by either remedy.

**ADHDev 하류 회피책, for reproduction**: a minimal repro against the current library — construct a `BeaconHub`-backed node, `beacon.start(stubTransport)`, append an entry and await the debounce (or call the internal push path), confirm one `put()`; then `handle.stop()`; `beacon.start(stubTransport)` again; append again and await the same debounce window; confirm zero further `put()` calls. No thrown error at either `start()` call.

**Status: implemented 2026-08-28** — **remedy 1** (`stop()` is a reusable pause), with the proposal's own caveat honored: `close()` keeps its stronger, terminal guarantee through a *separate* field. The single `stopped` boolean is gone, replaced by:

- **`closed`** — set only by `close()`, genuinely one-way. `start()` throws `misuse("beacon closed — the node is closed")` when it is set, so node-level teardown stays irreversible. This is the field that makes remedy 1 safe; a naive "just clear `stopped` in `start()`" patch would have made a closed node's hub re-armable, whose debounce timer would then call `core.vectors()` on a closed store — the §14 close-quiescence violation `close()` exists to prevent.
- **`armGen`** — a monotonic arming id, incremented by `start()`, by `stop()`, and by `close()`. It replaces the boolean's role in every remaining guard and additionally makes handles **per-arming**.

Item 3 is discharged by construction rather than by extending the `:53` check as written: the `if (this.transport) throw` guard is left exactly as it was (so the "beacon already started" path is unchanged, per regression (iii)), and the stopped-but-transport-nulled case it used to miss is now simply a legal re-arm rather than an error to detect.

Three things the proposal did not ask for, found while implementing and each regression-pinned:

- **A stale handle's `stop()` must not disarm a later arming.** A host that keeps the old handle across a re-arm — the natural mistake given `stop()`/`start()` is now a supported cycle — would otherwise tear down the live session. `stop()` compares its captured generation before acting, which also makes `stop()` idempotent for free.
- **A round answered after `stop()` must not overwrite `known`.** `push()`'s GET tail is async; a response landing after detach describes a board this hub no longer reports to. `push()` captures the generation and adopts only if it is still current. (The increment ordering matters: `start()` bumps `armGen` *before* its own initial `push()`, so that push's round is correctly current.)
- **Two latent leaks in the old teardown**, unrelated to the latch but adjacent: `stop()` cleared the debounce timer without nulling `debounceTimer`, and `close()` never nulled `hostHints`. Both are now nulled on every teardown path.

Regression: `test/beacon.test.ts` P28 block — (i) stop → start → append pushes again, asserted on a `put()` counter across both the re-arm's own report and the subsequent debounce; (ii) `close()` → `start()` throws, matched on `/beacon closed/` rather than a bare `/closed/` so a generic node-level guard cannot satisfy it by accident; (iii) double-start without an intervening stop still throws "beacon already started"; plus the stale-handle and in-flight-round cases above. Verified red before the fix: (i), (ii) and the stale-handle case all fail against the pre-P28 code, and the in-flight case fails against a version carrying only the latch fix.
